01

検索の仕組み — 索引を引くAPI

Highlighted Content Web Part に専用APIはない。内部で /_api/search(Search REST API)を呼んでいるだけなので、同じAPIを直接使えば同じことができる。そしてこのAPIはリストAPIと決定的に違う。元データを読まず、クローラーが作った検索インデックス(索引)だけを見る。

この一点からすべての性質が導かれる。

  • テナント横断できる — 索引は全サイト分ある。スコープ指定なしなら全サイトのニュースが対象
  • 速い — 元データを読まない
  • 公開直後は出ない — 索引の更新(クロール)に時間差がある
  • 列名がそのまま使えない — 索引には「管理プロパティ」という別名で載る(→ 03章)

ニュースページの識別は PromotedState:2(0=通常ページ / 1=昇格候補 / 2=公開済みニュース)。Highlighted Content Web Part も内部で人物プロファイル除外(-ContentClass=urn:content-class:SPSPeople)を自動付加しており、Webパーツと生クエリの結果が微妙に違う原因のひとつになっている。

02

リクエストの基本形 — 3つの質問

URLは長くて威圧的だが、骨格は3つの質問に答えているだけ。「ニュースを探して、タイトルとURLだけ、10件ちょうだい」。

GET /_api/search/query?
  querytext='PromotedState:2'          ← ① 何を探す?(KQL)
  &selectproperties='Title,Path'       ← ② 何の情報が欲しい?
  &rowlimit=10                         ← ③ 何件欲しい?

実用でよく足すのは並び順と、JSONで受けるためのヘッダー。

// ニュース一覧の実用形(ブラウザConsoleから)
const res = await fetch(
  "/_api/search/query?querytext='PromotedState:2'" +
  "&selectproperties='Title,Path,Author,FirstPublishedDate," +
  "PictureThumbnailURL,SiteTitle,Description'" +
  "&sortlist='FirstPublishedDate:descending'&rowlimit=20",
  { headers: { Accept: "application/json;odata=nometadata" } }
);
パラメータ役割・注意点
querytextKQL条件。プロパティ:値 を AND / OR / NOT で連結。日本語やダブルクォートを含むときは encodeURIComponent 必須(→ 06章の失敗例)
selectproperties返すプロパティの指定。公開日 FirstPublishedDate は既定で返らないので明示する。Write は更新日なので公開日表示に使うと編集のたびに動く
sortlist既定は関連度(Rank)順で新着順ではない。ニュース一覧なら FirstPublishedDate:descending がほぼ必須
rowlimit既定10件。件数の全体は TotalRows で確認
trimduplicates既定 true。内容がほぼ同一のページは畳まれる。「あるはずのページが出ない」ときは false を試す
refiners / refinementfiltersカテゴリごとの件数集計と絞り込み。使えるのは Refinable な管理プロパティのみ(→ 04章)

KQLのスコープ指定パターン

Path:https://tenant.sharepoint.com/sites/xxx/* — 特定サイト配下に限定

DepartmentId:{hubSiteId} — ハブサイト配下に限定

TabCategory:* — 値が入っているものだけ(null除外)

03

プロパティの一生 — 列がKQLで使えるようになるまで

最大のつまずきポイント。リストに「カテゴリ」列を作っても querytext='カテゴリ:お知らせ' は動かない。列の値は3段階の加工ラインを通って初めて検索で使える名前になる。

用語正体
クロールクローラーが数分〜数十分おきにテナントを巡回し、変更アイテムを索引へ運ぶ裏方プロセス。「再インデックス」は次の巡回で全件読み直す予約
クロールプロパティクロール時に列から自動生成される生メモ。ows_内部名 形式。KQLからは直接参照できない。値が入ったアイテムが実際にクロールされて初めて生成される
管理プロパティ検索エンジンが公式に受け付ける窓口。Title や PromotedState が最初から使えるのはMicrosoftがマッピング済みだから。独自列は自分でマップする
マッピング「生メモ○○を窓口△△に転記せよ」というルール登録。1つのクロールプロパティを複数の管理プロパティにマップ可能
PITFALL — 日本語列名の罠

クロールプロパティは表示名ではなく内部名から作られる。日本語で列を作ると内部名は _x30ab__x30c6_... のようなエンコード文字列になり、「ows_カテゴリ」で検索しても永遠にヒットしない。

内部名の確認:ライブラリ設定 → 列をクリック → URLの Field= 以降。定石は英語名で列を作ってから表示名を日本語に変える(内部名は英語のまま残る)。今回のテナントは TABCATEGORY という英語内部名だったため ows_TABCATEGORY がそのまま見つかった。

PITFALL — 列の型で格納形式が変わる

選択肢(単一)・1行テキストは入力値そのまま。複数選択可は 値;#値 形式で入ることがある。管理メタデータ列は GP0|#GUID 形式になり文字列マップでは実用にならない(owstaxId〜 系を使う)。

なぜ二段構えなのか:テナント内には同名の列が無数にある。生メモ層で各サイトの実態を吸収し、窓口層で1つのテナント共通名に集約するから、複数サイトの「カテゴリ」列を横断で同じKQLで検索できる。ただし集約されるのは内部名が揃っている場合のみ。サイトごとに手作りすると内部名がズレて別のクロールプロパティに分かれるので注意。

04

管理プロパティの設定 — 2つの選択肢と制約

マッピング先は2通り。実務では両方にマップする両取りが定石(1つのクロールプロパティは複数の管理プロパティへマップできる)。

自作プロパティ
TabCategory		予約スロット
RefinableString00〜99
KQL絞り込み○(Queryable有効化が条件)○
refiner集計×(構造上不可)○
ソート×(構造上不可)○
クエリの可読性◎ TabCategory:"ツール"△(エイリアスで緩和可)

SharePoint Onlineでは自作プロパティを Refinable / Sortable にできない。Refinable系が RefinableString00 のような予約名で大量に事前確保されているのは、これらがインデックスの物理構造に関わるため。

自作プロパティで必ず確認するチェックボックス

  • Queryable(クエリ可能) — 無効だとKQLで指定してもエラーにならず黙って無視される。最重要
  • Retrievable(取得可能) — 無効だと selectproperties で値が返らない。デバッグの覗きクエリにも必要
  • Searchable — プロパティ名なしのフリーワード検索で当てたい場合のみ任意

設定手順(今回の実施内容)

  • SharePoint管理センター → 検索スキーマの管理 → 新しい管理プロパティ TabCategory を作成、Queryable / Retrievable を有効化
  • クロールされたプロパティへのマッピングで ows_TABCATEGORY を追加
  • 対象ライブラリ → 詳細設定 → 再インデックス(マッピングの後に実行。順番が逆だと転記されない)
  • 反映待ち:早ければ15分、混雑時は数時間
05

レスポンスの読み方 — 一本道とデバッグの目印

レスポンスは異様にネストが深いが、降りる道は毎回同じ。暗記対象は実質1行。Cells がKey-Value配列なのは、selectproperties で要求したものだけが動的に詰められる仕組みだから。

const rows = data.PrimaryQueryResult.RelevantResults.Table.Rows;
const items = rows.map(r =>
  Object.fromEntries(r.Cells.map(c => [c.Key, c.Value]))
);
// これでリストAPIと同じ感覚のオブジェクト配列になる

レスポンス内のデバッグ用シグナル

場所読み方
SerializedQuery の QueryText0件のとき最初に見る場所。ここが空ならクエリ自体がサーバーに届いていない(エンコード事故)。条件の問題以前の話
QueryModification実際に実行されたクエリ。自動付加された除外条件もここで分かる
TotalRowsヒット総数。RowCount は今回返った件数
TotalRowsIncludingDuplicates重複除去前の件数。差分 = 畳まれたページ数
Rank関連度スコア。sortlist 指定時はソートキーがエンコードされた巨大な値になり、意味を持たなくなる
HasParseExceptionKQLの構文エラー検知
PITFALL — URLエンコード事故

日本語+ダブルクォート+ANDスペースの組み合わせをアドレスバーに直貼りすると、querytext が壊れて空文字で届くことがある。結果は「エラーなしの0件」で、条件の問題と区別がつかない。

対策:KQL全体を encodeURIComponent でエンコードする(APIの構文である外側のシングルクォートは対象外)。そして0件のときはまず SerializedQuery を確認する習慣をつける。

06

検証ログ — 実テナントでの全工程

実際に踏んだ手順と結果。失敗も含めてすべてが切り分けの材料になった。

  1. 成功最小クエリで疎通確認 querytext='PromotedState:2'

    TotalRows 253件。3サイト(NewsPages / xsp-feature / mare-group)が混在し、テナント横断を確認。重複除去前は353件で、100件が畳まれていることも判明。並びはRank順で新着順ではない。

  2. 成功プロパティ明示+新着順ソート selectproperties + sortlist

    FirstPublishedDate の完全降順に。既定では返らない公開日が取得でき、レスポンスもスリム化。副産物としてコピーページ(〜(1).aspx)の重複と、Descriptionの繰り返し設定ミスを発見。

  3. 失敗クロールプロパティが見つからない ows_列名 → 0件

    検索スキーマで「ows_カテゴリ」がヒットせず。原因は表示名で探していたこと。内部名を確認すると英語の TABCATEGORY で、ows_TABCATEGORY が存在した。「ows_」だけで検索して一覧を目視するのが確実。

  4. 失敗絞り込み0件 RefinableString00:"お知らせ"

    AND条件込みの0件では原因が見えない。絞り込みを外して値だけ覗くクエリに切り替える方針へ。後に判明した真因は「お知らせ」という値がそもそも存在しなかったこと(実在値は Coliss / デザイン / ツール)。

  5. 成功覗きクエリで転記確認 selectproperties='Title,TabCategory'

    自作管理プロパティ TabCategory(Queryable + Retrievable)へのマッピング+再インデックス後、値の転記を確認。日本語値「デザイン」も文字化けなし。実在するカテゴリ値の棚卸しができた。

  6. 失敗エラーなしの0件 QueryText=""

    日本語込みのURLを直貼りした結果、SerializedQuery の QueryText が空でサーバーに到達。クエリが届いていないだけで、マッピングにも値にも問題なし。encodeURIComponent で解決。

  7. 達成カテゴリ絞り込み完成 TabCategory:"ツール" → 23件

    全件がTabCategory「ツール」で返り、当初の目標(テナント横断ニュース取得+カテゴリ絞り込み)を完全達成。

08

最終コード

到達した完成形。サイト内ページのConsole・SPFx・外部アプリ(要認証)でそのまま使える。

async function getNews({ category = null, count = 20 } = {}) {
  let kql = "PromotedState:2";
  if (category) kql += ` AND TabCategory:"${category}"`;

  const res = await fetch(
    `/_api/search/query?querytext='${encodeURIComponent(kql)}'` +
    `&selectproperties='Title,Path,Author,FirstPublishedDate,` +
    `PictureThumbnailURL,SiteTitle,Description,TabCategory'` +
    `&sortlist='FirstPublishedDate:descending'&rowlimit=${count}`,
    { headers: { Accept: "application/json;odata=nometadata" } }
  );
  const data = await res.json();

  // デバッグ:0件のときはまずここを見る
  // console.log(data.Properties.find(p => p.Key === "SerializedQuery")?.Value);

  return data.PrimaryQueryResult.RelevantResults.Table.Rows.map(r =>
    Object.fromEntries(r.Cells.map(c => [c.Key, c.Value]))
  );
}

// 使い方
const all   = await getNews();                        // 全ニュース新着順
const tools = await getNews({ category: "ツール" }); // カテゴリ絞り込み → 23件

開発のコツ:Highlighted Content Web Part を配置したページを開発者ツールで開き、Networkタブの /_api/search/postquery を見ると、Webパーツが実際に投げているQueryTemplateやSelectPropertiesをそのまま確認できる。記事より確実な一次情報。

10

操作リファレンスとKQL入門

4つの関係を一文で:KQLで聞ける名前を作るのが管理プロパティ登録、その値を索引に運ぶのがクロール、運ばせる予約が再インデックス、インデックス登録そのものは全自動。以下、それぞれの実際の操作。

クロールを実行する — 正確には「予約する」

SharePoint Onlineにクロールの手動実行ボタンは存在しない。オンプレ版にあった「フルクロール開始」は管理者にも開放されておらず、クローラーはMicrosoft管理の継続的クロール(数分〜十数分間隔)で自動巡回している。できるのは「次の巡回で全件読み直してもらう予約」=再インデックスのみ。

スコープ操作場所
ライブラリ / リスト単位ライブラリ設定 → 詳細設定 → 「ドキュメント ライブラリの再インデックス」。マッピング変更後の転記にはこれで十分
サイト単位サイト設定 → 「検索と可用性」 → 「サイトの再インデックス」。サイト列変更など広範囲に効かせたいとき
PnP PowerShell下のコピペ用スニペット参照。複数ライブラリ・複数サイトの一括処理はこちらが速い

PnP PowerShell — 再インデックス一式(接続 → リスト単位 → サイト単位)

# 事前準備(未導入なら1回だけ)
Install-Module PnP.PowerShell -Scope CurrentUser

# 対象サイトへ接続({tenant} {site} を置き換え)
Connect-PnPOnline -Url https://{tenant}.sharepoint.com/sites/{site} -Interactive

# ライブラリ / リスト単位の再インデックス
Request-PnPReIndexList -Identity "サイトのページ"

# サイト単位の再インデックス(サイト内の全リストが対象)
Request-PnPReIndexWeb

# 切断
Disconnect-PnPOnline

PnP PowerShell — 複数サイトを一括再インデックス(カテゴリ列を横展開した後など)

$sites = @(
  "https://{tenant}.sharepoint.com/sites/NewsPages",
  "https://{tenant}.sharepoint.com/sites/xsp-feature",
  "https://{tenant}.sharepoint.com/sites/Share-Point/mare-group"
)
foreach ($url in $sites) {
  Connect-PnPOnline -Url $url -Interactive
  Request-PnPReIndexList -Identity "サイトのページ"
  Write-Host "再インデックス予約: $url"
  Disconnect-PnPOnline
}

仕組み:これらの操作は vti_searchversion プロパティを+1しているだけ。クローラーは巡回時にこの番号の上昇を見て「全アイテム読み直し」と判断する。つまり即時実行ではなくあくまで予約で、反映は15分〜数時間後。なお、アイテムの通常の編集・公開は次の巡回で自動クロールされるため、再インデックスが必要なのは「アイテムは変わっていないのに索引の作り方(マッピング)を変えた」ときだけ。

検索インデックスに登録する — 「する」ものではなく「される」もの

インデックスへの登録操作は存在しない。登録は常にクロールの副産物として自動で起きる。コントロールできるのは「登録される条件を整える」ことと「登録させない」ことだけ。

やりたいこと方法
登録する操作不要。検索可能な場所に置き、閲覧権限があり、公開されていれば次の巡回で自動登録される
除外する(サイト)サイト設定 → 検索と可用性 → 「このサイトを検索結果に表示する」をいいえ
除外する(リスト)詳細設定 → 「このライブラリのアイテムを検索結果に表示する」をいいえ
登録済みか確認Search APIで覗く:querytext='Path:"https://.../ページ名.aspx"' — 0件なら未クロールか除外設定

新しい管理プロパティを登録する — 完全手順

場所:SharePoint管理センター → その他の機能 → 検索 → 検索スキーマの管理。

  • 「管理プロパティ」タブ → 「新しい管理プロパティ」。名前は英数字のみ・後から変更不可(例:TabCategory)
  • 型を選択(テキスト列由来なら「テキスト」)
  • クエリ可能(Queryable)にチェック — 忘れるとKQLで黙って無視される
  • 取得可能(Retrievable)にチェック — 忘れると selectproperties で値が返らない
  • 「クロールしたプロパティへのマッピング」→ ows_TABCATEGORY を検索して追加 → 保存
  • 対象ライブラリで再インデックス(マッピング保存の後に実行。順番が逆だと転記されない)
  • 15分〜数時間待って覗きクエリで転記確認

Refinable / Sortable が必要な場合(自作では不可)

新規作成ではなく予約スロット RefinableString00〜99 を編集してマッピングを追加する。「エイリアス」欄に別名(例:TabCategoryRef)を入れるとKQLの可読性を保てる。

空きスロットはマッピング欄が空かどうかで確認。テナント共有資源なので他用途との衝突に注意。複数テナント展開なら Get-PnPSearchConfiguration / Set-PnPSearchConfiguration でスキーマXMLを持ち回るのが確実。

KQLとは何か

Keyword Query Language。SharePoint検索(Microsoft Search全般)への問い合わせ専用言語で、querytext の中身がこれ。SQLのような重厚な言語ではなく、Googleに site:example.com filetype:pdf と打つ感覚に近い検索特化の軽量文法。構成要素は3種類だけ。

// ① フリーテキスト — 全文(Searchableなプロパティ)から探す
防災訓練
"防災 訓練"                          ← フレーズ完全一致

// ② プロパティ制限 — Queryableな管理プロパティのみ使える
PromotedState:2
TabCategory:"ツール"
FirstPublishedDate>=2026-07-01       ← 比較演算子 = : < > <= >=
Title:CSS*                            ← 前方一致ワイルドカード
TabCategory:*                         ← 値が存在する(null除外)

// ③ 演算子 — 必ず大文字(小文字だとただの検索語扱い)
PromotedState:2 AND TabCategory:"ツール"
TabCategory:"ツール" OR TabCategory:"デザイン"
PromotedState:2 NOT Path:https://tenant.sharepoint.com/sites/test/*
(A OR B) AND C                       ← カッコでグループ化

コロン : は「含む」、イコール = は「完全一致」。これだけで実務の9割はカバーできる。残り(NEAR近接検索、XRANKランク調整など)は必要になったときに KQL syntax reference を引けば十分。兄弟言語のFQLもAPIは受け付けるが、KQLで足りない場面はまずない。HCWPカスタムクエリで登場したCAMLは検索ではなくリスト直接クエリの言語なので、Search API側では使わない。

コピペで使える検証URL集

{tenant} を自テナント名に置き換えれば、サインイン済みブラウザのアドレスバーにそのまま貼って動く。日本語を含むものはエンコード済み。Console用の相対パス版はページ下のスニペットを使う。

① 疎通確認 — ニュースが何件あるか(TotalRowsを見る)

https://{tenant}.sharepoint.com/_api/search/query?querytext='PromotedState:2'

② 新着順ニュース一覧 — 実用フル版(公開日・サムネイル付き)

https://{tenant}.sharepoint.com/_api/search/query?querytext='PromotedState:2'&selectproperties='Title,Path,Author,FirstPublishedDate,PictureThumbnailURL,SiteTitle,Description'&sortlist='FirstPublishedDate:descending'&rowlimit=20

③ 覗きクエリ — 管理プロパティに値が転記されたか確認(絞り込みなし)

https://{tenant}.sharepoint.com/_api/search/query?querytext='PromotedState:2'&selectproperties='Title,TabCategory'&rowlimit=10

④ カテゴリ絞り込み — 日本語値のエンコード済み例(TabCategory:"ツール")

https://{tenant}.sharepoint.com/_api/search/query?querytext='PromotedState%3A2%20AND%20TabCategory%3A%22%E3%83%84%E3%83%BC%E3%83%AB%22'&selectproperties='Title,TabCategory,FirstPublishedDate'&sortlist='FirstPublishedDate:descending'&rowlimit=20

⑤ 特定ページの登録確認 — 0件なら未クロールか除外設定

https://{tenant}.sharepoint.com/_api/search/query?querytext='Path:"https://{tenant}.sharepoint.com/sites/{site}/SitePages/{page}.aspx"'

⑥ 重複込み全件 — 「あるはずのページが出ない」ときの切り分け

https://{tenant}.sharepoint.com/_api/search/query?querytext='PromotedState:2'&trimduplicates=false&rowlimit=50

⑦ Console用スニペット — 相対パスで実行し、SerializedQueryと結果を同時確認

const kql = `PromotedState:2 AND TabCategory:"ツール"`;
const res = await fetch(
  `/_api/search/query?querytext='${encodeURIComponent(kql)}'` +
  `&selectproperties='Title,TabCategory,FirstPublishedDate'` +
  `&sortlist='FirstPublishedDate:descending'&rowlimit=20`,
  { headers: { Accept: "application/json;odata=nometadata" } }
);
const data = await res.json();
console.log(data.Properties.find(p => p.Key === "SerializedQuery")?.Value);
console.table(
  data.PrimaryQueryResult.RelevantResults.Table.Rows.map(r =>
    Object.fromEntries(r.Cells.map(c => [c.Key, c.Value]))
  )
);

ブラウザ直貼りの結果はXMLで表示される。JSONで見たい場合は⑦のConsoleスニペットを使う(Acceptヘッダーが必要なため)。0件が返ったら、まず SerializedQuery の QueryText が空でないかを確認すること。
